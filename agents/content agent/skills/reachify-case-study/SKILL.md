# Case Study — Outcome-Led B2B Narrative

**Source:** Acefone's Pickrr case study (acefone.com/case-studies/pickrr) — authored by Ritwik for a B2B platform audience. This is a first-party, trusted source rather than a third-party benchmark. Only content depth, structural order, and writing style were extracted; Acefone's visual branding, layout styling, and colours are explicitly excluded and are not part of this template.

## When to use

Use this shell for any B2B case study or customer success story — the flagship BOFU proof asset. It works as a standalone web page (short, scannable, stat-led) and can be expanded into a longer downloadable/PDF version by fleshing out the "Solution narrative" module. Default to the lean web version; add depth only where the client has real detail to share.

## Structure

1. **Headline — outcome as the hook.** Lead with the single biggest quantified result, framed as an achievement, not a feature. Pattern: "How [Client] Achieved [Big Number/Outcome]" (e.g. "How Pickrr Achieved 2X Order Conversion"). Never lead with the product name.
2. **Subheadline — one line of context.** Who the client is (industry/category) + what specific workflow or problem area improved. One sentence, no jargon overload.
3. **Opening paragraph — client + tension in 2–3 sentences.** Sentence 1: who the client is and what they do (their own words/positioning, not benchmark boilerplate). Sentence 2: what their growth/scale depended on. Sentence 3: the "however" — what broke or stopped scaling as they grew. This is the entire client-background module; do not write a separate long "About [Client]" section.
4. **Challenges — 5–6 bullets, not prose.** Short noun-phrase pain points (2–5 words each), each naming a concrete operational symptom, not an abstract complaint. Pattern: "Ad-hoc outbound calls", "No call recordings or tracking", "Manual [process] confirmation", "Inconsistent follow-ups", "Limited visibility", "Hard to scale without headcount". Order roughly from tactical pain to strategic pain.
5. **Results — stat callouts, front-loaded, before the solution is explained.** 4–6 large-typography numbers, each 2–4 words, mixing types: one headline multiplier ("2X Order Conversion"), volume stats ("100k+ Voice Bot Calls Handled"), rate/quality stats ("40% Dialer Answer Rate", "<1% Service Downtime"), and a speed stat ("3X Faster Order Confirmation"). Deliberately place Results before the solution walkthrough — this is a proof-first structure, not a chronological one.
6. **Solution narrative — [OPTIONAL, expand or keep lean].** Lean version (default, matches the benchmark): one sentence naming the category of solution used (e.g. "voice automation and dialer workflows") without a full product walkthrough, optionally pointing to a downloadable long-form asset. Detailed version (use when the client wants a long-form/PDF case study, or when there's enough input to write it credibly): 2–4 short paragraphs or subheads walking through what was implemented, in the same order the challenges were listed, closing the loop on each pain point named in module 4.
7. **Testimonial — one quote, placed after the results/before the close.** Direct quote from a named role (title + company, not full name required), referencing the specific workflow and the specific outcome — never a generic "great product" quote. Pattern: "With [Solution], our [workflow] became fully structured... [outcome in the client's own words]." — [Role], [Client].
8. **Closing CTA — short, forward-looking, not salesy.** A one-line aspirational statement ("You're at the start of something special.") followed by a single clear action ("Explore our [category] solutions today") and a contact/demo form. Avoid stacking multiple competing CTAs at the close — one action only.

## Copy rules (from benchmark)

- Keep total on-page word count lean: ~250–350 words excluding the stat callouts and testimonial. This is a scan-and-convert asset, not a long-form story — depth lives in stat density and specificity, not paragraph count.
- Every challenge bullet and every result stat should be able to be paired: for each pain point, there should be a traceable improvement, even if the mapping isn't spelled out explicitly on the page.
- Use industry-specific terminology naturally (the benchmark uses "COD", "dialer", "voice bot") — don't dumb down domain vocabulary for a B2B technical buyer, but don't over-explain it either.
- Favour short, active-voice sentences. Avoid hedging words ("could", "might", "potentially") in the results section — results are stated as fact.
- Numbers are always the visual hero of the page — never bury a stat inside a paragraph when it can be its own callout.
- Tone: professional, confident, no hyperbole or superlatives beyond what the data supports.

## Fields to fill per client/article

- [ ] Client name + one-line industry/category description
- [ ] Headline outcome stat (the single number the whole page is built around)
- [ ] Subheadline (client type + workflow area improved)
- [ ] Opening 3-sentence client + tension paragraph
- [ ] 5–6 challenge bullets (short noun phrases)
- [ ] 4–6 result stat callouts (mix of multiplier / volume / rate / speed)
- [ ] Decision: lean solution line vs. detailed solution narrative (and if detailed, subheads per challenge)
- [ ] Testimonial quote + role + client name (get sign-off before publishing)
- [ ] Closing CTA line + single action + contact/demo form
- [ ] Client logo/name usage approval on file
